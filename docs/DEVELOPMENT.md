# 개발 규칙과 다음 작업 순서

## 1. 개발을 시작하기 전

새로운 노트북이나 새로운 세션에서 바로 코드를 수정하지 않는다.

1. `docs/PROJECT_HANDOFF.md` 읽기
2. 현재 `git status --short --branch` 확인
3. 테스트 실행
4. 관련 모듈과 기존 Trace 계약 확인
5. 변경 범위와 검증 방법을 정한 뒤 수정

현재 원격 저장소:

```text
https://github.com/hohyunle/jeonja_chilpan.git
```

## 2. 기준 검증 명령

```powershell
.\.venv\Scripts\python.exe -m unittest discover -s tests -v
.\.venv\Scripts\python.exe -m compileall -q app tests
.\.venv\Scripts\python.exe -m pip check
```

UI를 변경했으면 최소한 위 테스트와 offscreen UI 생성 테스트를 실행한다. OCR을
변경했으면 모델이 있는 PC에서 한국어 이미지 테스트와 실제 `OcrWorker` 경로를 함께
확인한다. 듀얼모니터를 변경했으면 실제 두 모니터에서 캡처 위치를 확인한다.

## 3. 코딩 원칙

### 실행기

- 전체 Python을 지원하려고 하지 않는다.
- Parser가 허용하지 않은 문법은 Executor에 도달하지 않게 한다.
- `exec`, `eval`, `subprocess`, 임의 import를 추가하지 않는다.
- 실행 제한을 제거하지 않는다.
- 실행 중 상태를 사용자에게 보여줄 필요가 있으면 Step/Trace 계약부터 설계한다.

### Step

Step은 다음 원칙을 따른다.

> 학습자가 프로그램의 상태 변화 또는 제어 흐름의 변화를 이해할 수 있는 최소한의
> 의미 있는 실행 단위.

`x = 10`을 `x 읽음`, `10 읽음`, `대입` 같은 토큰 단위로 쪼개지 않는다. 반대로 여러
줄의 서로 다른 상태 변화를 한 Step으로 뭉개지도 않는다. 프로토타입하면서 조정하되,
시각화 장면이 설명하려는 의미와 일치해야 한다.

### Trace와 시각화

- Executor는 `TraceStep`에 실제 실행 사실만 기록한다.
- Visualizer는 Trace만 받아 표시한다.
- 화면 디자인 예시의 fixture 값으로 빈 Trace를 채우지 않는다.
- 새 시각화는 실제 Trace detail 필드가 있을 때만 활성화한다.
- 템플릿 라이브러리를 사용자 UI에 다시 노출하지 않는다. 현재는 Trace가 장면을 자동 선택한다.

### OCR

- OCR 결과는 편집창을 거쳐야 한다.
- 한국어 모델은 `korean_PP-OCRv5_mobile_rec`를 기준으로 한다.
- 모델 파일을 Git에 올리지 않는다.
- 예열과 추론을 다른 스레드에서 수행하도록 바꾸지 않는다.
- 정확도 개선은 실제 수업자료 캡처로 확인한다.

### UI

- 메인 화면은 짧은 흐름과 명확한 버튼을 우선한다.
- 화면 선택 중 PDF/PPT가 보이지 않을 정도의 음영을 사용하지 않는다.
- 코드 영역은 고정폭 글꼴, 한글 안내는 설치 글꼴 자동 선택을 사용한다.
- 전자칠판 전용 API를 추가하기 전에 현재 마우스 이벤트 흐름을 보존한다.

## 4. 기능 추가 절차

### 새 Python 문법

1. `parser.py`의 허용 AST 노드와 validator 규칙 추가
2. `executor.py`의 안전한 평가/실행 규칙 추가
3. 의미 있는 Step kind와 details 정의
4. `models.py` 문서와 Trace 계약 갱신
5. 성공/오류/제한 테스트 추가
6. Visualizer 장면 또는 증거 표시 연결
7. README와 docs 갱신

### 새 시각화 장면

1. 어떤 Trace 사실이 필요한지 먼저 정의
2. Executor가 그 사실을 실제로 기록하는지 확인
3. `template_library.py`에 메타데이터 추가
4. `_available_template_keys`에 활성 조건 추가
5. `_template_html` 계열 렌더러 추가
6. 빈 상태, 오류, Step 이동, 상태 변화 테스트
7. fixture 값이 아니라 실제 Executor Trace로 screenshot 확인

### OCR 변경

1. 모델 이름·폴더 구조·오프라인 경로 확인
2. 작은 한국어/영어/숫자 샘플로 인식
3. Python 기호(`:`, `>=`, `()`, 따옴표, `_`) 샘플로 인식
4. 들여쓰기 복원과 같은 줄 조각 병합 확인
5. 예열 후 첫 요청과 두 번째 요청 시간을 비교
6. OCR 오류가 UI를 종료시키지 않는지 확인

### 듀얼모니터 변경

1. 전역 좌표와 모니터 로컬 좌표를 분리해서 기록
2. 주/보조 모니터, 음수 좌표, 역방향 드래그를 확인
3. 모니터별 DPI 배율이 다를 때 캡처 크기를 확인
4. 선택 모니터 경계 제한을 유지
5. 실제 캡처 미리보기로 최종 확인

## 5. 우선순위가 높은 다음 작업

### P0 — 실제 장비/사용성 검증

- 실제 Windows 11 노트북에서 새 환경 설치 재현
- 듀얼모니터 배치별 캡처 테스트
- 실제 PDF/PPT 강의자료로 OCR 샘플 수집
- 한글 주석과 Python 기호 정확도 표 작성
- 전자칠판 또는 터치 모니터에서 터치-마우스 이벤트 확인
- 실행 파일을 다른 사용자 경로에서 실행하는지 확인

### P1 — 제품 완성도

- OCR 결과의 낮은 confidence 표시 또는 재선택 안내
- OCR 인식 실패 시 선택 영역 확대/축소 도움말
- Visualizer의 장면별 설명 문장 개선
- 실행 오류와 지원하지 않는 문법의 사용자 메시지 통일
- 배포 PC에서 모델 설치/복사 과정을 더 단순하게 만들기
- 실제 장비 테스트 결과를 회귀 테스트/문서에 기록

### P2 — Trace 기반 템플릿 확장

현재 Executor가 실제로 제공하는 정보부터 확장한다.

- 리스트를 넘어 2차원 배열
- 스택/큐/연결 리스트는 먼저 자료구조 표현과 Trace 계약 정의
- 정렬/탐색은 비교·교환·범위 축소 Step 정의
- 동적 계획법은 의존 셀과 계산 근거 Step 정의
- 함수/재귀는 현재 실행 제한과 지원 정책을 명확히 한 뒤 확장
- 비동기/동시성은 실제 스케줄링 Trace가 생기기 전에는 구현하지 않음

## 6. Git 작업 흐름

수정 전:

```powershell
git status --short --branch
```

검증 후:

```powershell
git add app tests docs README.md
git commit -m "Describe the change"
git push origin main
```

`.venv`, `build`, OCR 모델 바이너리, 캐시를 커밋하지 않는다. 변경 내용이 여러 주제에
걸치면 한 커밋에 섞지 말고 기능별로 나눈다.

## 7. 완료 기준

기능을 “완료”라고 하기 전에 다음을 확인한다.

- 기존 테스트가 통과한다.
- 실패/취소/빈 입력 경로가 있다.
- UI가 실행기 내부 구현에 직접 의존하지 않는다.
- 인터넷이 끊겨도 모델이 준비되어 있으면 동작한다.
- 실제 Trace에 근거하지 않은 시각화 값이 없다.
- 문서와 실행 명령이 현재 코드와 일치한다.
- 듀얼모니터/터치 관련 제한을 과장하지 않는다.
